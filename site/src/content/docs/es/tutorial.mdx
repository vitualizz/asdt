# Tutorial: Tu primer pipeline

En este tutorial vas a instalar ASDT, hacerle una primera pregunta a un especialista sobre un repo que ya tenés, y recién después correr una entrega completa PM → Arquitecto → Developer para una feature concreta: **agregar un formulario de contacto con validación**.

ASDT funciona con dos asistentes de IA — **Claude Code** y **OpenCode**. Los pasos de abajo son idénticos para ambos; donde difieren (ubicación de la configuración, reinicio, autenticación) se muestran ambos lado a lado. Elegí el que uses.

Tiempo estimado: 15 minutos.

<TutorialPipelineStepper lang="es" />

## Requisitos

Antes de empezar, asegurate de tener:

- **Claude Code** u **OpenCode** instalado y autenticado. Si tu sesión expiró, volvé a autenticarte con el flujo de login de tu asistente (`claude` para Claude Code, `opencode` para OpenCode).
- **Engram** instalado (el instalador lo verifica) y conectado a la configuración MCP de tu asistente, para que las decisiones clave pasen a la sesión siguiente. Si en una sesión no está conectado, ASDT igual funciona dentro de esa sesión. Ver [Scratchpad y memoria](/asdt/es/docs/memory-and-engram) para el setup.
- Una terminal **bash o zsh**.

## Paso 1 — Instalar ASDT

Ejecutá el script de instalación:

```bash
curl -fsSL https://raw.githubusercontent.com/vitualizz/asdt/main/install.sh | bash
```

El binario se coloca en `~/.local/bin/asdt-tui`. Si tu shell no lo encuentra, agregá esto a tu shell profile:

```bash
export PATH="$HOME/.local/bin:$PATH"
```

Después instalá las skills de los especialistas en tu asistente:

```bash
asdt-tui
```

Este menú interactivo te deja elegir tu(s) asistente(s) y copia los archivos de skill. Instala en:

- **Claude Code** → `~/.claude/skills` (agentes ejecutores en `~/.claude/agents/`)
- **OpenCode** → `~/.config/opencode/skills` (agentes ejecutores en `~/.config/opencode/agents/`, más wrappers de comandos en `~/.config/opencode/commands/`)

Luego **reiniciá tu asistente** — tanto Claude Code como OpenCode cargan las definiciones de skills (y comandos) al iniciar.

Si `asdt-tui` muestra `command not found`, ver [Solución de problemas](/asdt/docs/troubleshooting).

## Paso 2 — Inicializar ASDT en tu proyecto

Abrí tu asistente (Claude Code u OpenCode) en el directorio de tu proyecto y ejecutá:

```text
/asdt-init
```

Esto detecta tu stack y tus convenciones y los escribe, junto con la configuración del memory provider, en `.asdt/config.yaml`, para que cada especialista adapte su output a tu proyecto. En el camino te pregunta para qué superficie diseña primero el proyecto — mobile, tablet, desktop, o none si no tiene UI.

## Paso 3 — Preguntale algo a un especialista

Antes de construir nada, probá el camino más corto. Apuntá un especialista a código que ya tenés:

```
/asdt-security "audita cómo manejamos las sesiones"
```

Lee el código que corresponde y te cuenta en prosa qué encontró. Con la memoria conectada, recuerda los hallazgos clave de la auditoría como notas cortas: lo que corras después sobre esa área ya arranca sabiéndolos. No se planificó nada, no se ruteó nada — una pregunta, una respuesta.

Todos los especialistas funcionan así. `/asdt-architect "¿esta estructura escala?"`, `/asdt-qa "¿qué no cubren nuestros tests?"`. Eso es todo, y muchos días es lo único que vas a necesitar.

El resto del tutorial es la otra mitad: pasarle al equipo algo para construir.

## Paso 4 — Pedirle a ASDT una recomendación de pipeline

En tu asistente, ejecutá:

```text
/asdt "Agregar un formulario de contacto con validación"
```

ASDT analiza tu petición, recomienda qué especialistas involucrar y en qué orden, y te pregunta si corre esa cadena.

```text
# Output de ejemplo — tus resultados variarán según tu proyecto

Analizando: "Agregar un formulario de contacto con validación"

Pipeline recomendado:
  1. /asdt-pm        → Definir alcance y criterios de aceptación
  2. /asdt-architect → Diseñar el enfoque de validación y el contrato de la API
  3. /asdt-developer → Implementar el handler del formulario y la lógica de validación

Trabajo: contact-form

¿Corro la cadena? Voy de a un especialista por vez y hago una pausa después
de cada uno, para que puedas discutir antes de que arranque el siguiente.
```

Si decís que sí, `/asdt` corre la cadena por vos y hace una pausa después de cada especialista. O ejecutás vos cada comando, como hacen los pasos siguientes. El trabajo es el mismo: cada especialista lee los resúmenes de los anteriores.

## Paso 5 — Correr el Product Manager

```text
/asdt-pm "Agregar un formulario de contacto con validación"
```

El PM fija el alcance y escribe las historias de usuario. Su resumen va al scratchpad de la sesión, donde lo leen los especialistas siguientes (ver [Scratchpad y memoria](/asdt/es/docs/memory-and-engram)).

```text
# Output de ejemplo — tus resultados variarán según tu proyecto

Corriendo especialista PM...

Resumen: pm

  Feature: Formulario de contacto con validación
  
  Historias de usuario:
    US-01: Como visitante, quiero enviar un formulario de contacto para poder comunicarme con el equipo.
      AC1: Campos del formulario: nombre (requerido), email (requerido, formato válido), mensaje (requerido, máx 500 caracteres).
      AC2: El envío muestra un mensaje de éxito y envía una notificación por email.
      AC3: Los campos inválidos muestran mensajes de error en línea sin perder el input existente.
    
    US-02: Como visitante, quiero que el formulario impida el envío si mi email es inválido
      para no tener que esperar un rebote para saber que algo salió mal.
      AC1: El campo email valida el formato al perder el foco y al enviar.
      AC2: El botón de envío queda deshabilitado mientras existan errores de validación.

  En alcance: UI del formulario, validación del lado del cliente, handler de envío, notificación por email.
  Fuera de alcance: CAPTCHA, rate limiting, tracking de analytics.

Siguiente: /asdt-architect "Agregar un formulario de contacto con validación"
```

## Paso 6 — Correr el Arquitecto

```text
/asdt-architect "Agregar un formulario de contacto con validación"
```

El Arquitecto lee el resumen del PM, compara los enfoques técnicos entre sí y devuelve un único resumen: la decisión, las alternativas que descartó, y el modelo de datos y la superficie de API que se desprenden.

```text
# Output de ejemplo — tus resultados variarán según tu proyecto

Corriendo especialista Arquitecto...
Se basó en las historias y el alcance de Producto.

Resumen: architect

  Decisión: Usar la Constraint Validation API nativa del navegador para la validación de campos,
  complementada con una capa delgada de JS para mensajes de error personalizados y manejo del evento blur.
  
  Alternativas consideradas:
    - Validación con schema de Zod (rechazada: sobreingeniería para un formulario de contacto)
    - React Hook Form (rechazada: introduce una dependencia innecesaria)
  
  Superficie de API:
    - POST /api/contact — acepta { name, email, message }, devuelve 200 o 422
    - Notificación por email vía nodemailer (dependencia existente)
    - Sin escritura en base de datos — los datos del formulario se reenvían directamente por email

Siguiente: /asdt-developer "Agregar un formulario de contacto con validación"
```

## Paso 7 — Correr el Developer

```text
/asdt-developer "Agregar un formulario de contacto con validación"
```

El Developer lee los resúmenes del PM y del Arquitecto, explora el código y escribe un spec — alcance, criterios de aceptación y los archivos exactos que va a tocar. El spec pasa a ser su resumen y se te muestra: **no se escribe nada hasta que lo apruebes.** Si aprobás, implementa dentro de esos archivos y ningún otro; si pedís un ajuste, revisa el spec; si lo frenás, la corrida termina en el plan. `/asdt-developer "implementá el plan que aprobamos"` lo retoma más adelante y te lo vuelve a mostrar. Si la sesión terminó en el medio, el plan se reconstruye a partir de git, la memoria y tus palabras antes de que lo apruebes.

```text
# Output de ejemplo — tus resultados variarán según tu proyecto

Corriendo especialista Developer...
Se basó en los criterios de aceptación de Producto y el diseño de validación del Arquitecto.

Plan: resumen developer — stage: spec

  Va a crear:     src/components/ContactForm.astro
                  src/pages/api/contact.ts
                  src/styles/contact-form.css
  Va a modificar: src/pages/contact.astro

¿Aprobar, ajustar o frenar?  › aprobar

Resumen: developer — stage: implemented

¿Correr los chequeos ahora?  npm run lint · npm test  › sí
  ✓ todo pasó

Siguiente: /asdt-qa "Agregar un formulario de contacto con validación"
```

Los comandos de chequeo corren solo si decís que sí, y solo esos comandos — nunca se ofrece uno que reescriba archivos (un flag `--fix`, una actualización de snapshots). Si alguno falla, el Developer tiene hasta dos rondas para arreglarlo, dentro de los mismos archivos que aprobaste.

## Qué sigue

Tu pipeline está completo. Desde acá podés:

- Correr **[QA](/asdt/docs/specialists/qa)** (`/asdt-qa`) para validar la cobertura de los criterios de aceptación y generar un plan de pruebas.
- Correr **[Security](/asdt/docs/specialists/security)** (`/asdt-security`) para revisar el handler del formulario en busca de vulnerabilidades OWASP.
- Explorar **[Recetas](/asdt/docs/recipes)** para secuencias de comandos de otros escenarios comunes.
- Ver **[Solución de problemas](/asdt/docs/troubleshooting)** si algo salió mal.
