# AI Assistants

ASDT is not a standalone app. It installs **into** your AI assistant — it copies its specialist skills, generates executor agents, and wires up its configuration inside the tool you already use. The installer TUI (`asdt-tui`) does this for you and adapts each artifact to the assistant's native format.

Today ASDT supports two assistants: **Claude Code** and **OpenCode**. Both get the full specialist team; the difference is only in *where* files land and *what shape* they take.

## What gets installed

Regardless of assistant, an install produces the same logical pieces:

- **Specialist skills** — the ASDT skill tree (Researcher, PM, UX/UI, Architect, Developer, Security, QA, `/asdt-init`, and the shared fragments), copied into the assistant's skills directory.
- **Executor agents** — two generated agent definitions, `asdt-analyst` (read-only) and `asdt-builder` (write-capable), that carry out individual pipeline steps.
- **Agent config** — your persona, emoji, and language preferences, written as one marked block into the assistant's global config file (see [The agent config](#the-agent-config-both)).
- **An install manifest** — a `.install-meta.json` file recording what the last install wrote, so re-running can update cleanly and prune stale files.

The details of each piece differ per assistant. One term below is worth a plain-language note before you hit it: **`XDG_CONFIG_HOME`** is just the standard folder-location variable Linux/macOS tools check before falling back to a default config path.

## Claude Code vs OpenCode

### Why command wrappers only exist for OpenCode

Claude Code discovers and activates skills natively, so it needs no extra entry point — you call the specialist directly. OpenCode does not surface skills as slash-commands the same way, so ASDT generates a small command file per specialist that simply says "load and activate this specialist skill." This is why you'll see `~/.config/opencode/commands/` populated for OpenCode but no equivalent directory for Claude Code.

### Permission prompts (Claude Code)

ASDT never changes your Claude Code permission settings. To cut down on approval prompts, run Claude Code in **auto mode**: a classifier reviews each action, lets routine ones through, and blocks risky ones. It is the default starting mode for interactive sessions from Claude Code v2.1.283. ASDT's sub-agents (`asdt-analyst`, `asdt-builder`) inherit the session's auto mode, and the classifier also reviews the task handed to them, each of their tool calls, and the report they return.

ASDT's own consent gates are separate and stay in every mode: the Developer asks you to approve its plan before any file is written, and asks before running verification commands on your machine.

Never use `bypassPermissions` on your host machine: Claude Code reserves it for isolated containers and VMs.

For extra isolation, Claude Code's native sandbox (`/sandbox`) confines Bash at the OS level. On Linux it needs `bubblewrap` and `socat`; set `sandbox.failIfUnavailable: true` so a missing dependency fails instead of running unsandboxed.

OpenCode's executor agents carry their permissions inline: the analyst denies edits and restricts Bash to an inspection-only allowlist; the builder allows edits but denies delegation and the scratchpad; both deny the memory tools.

### The agent config (both)

If you pick a persona, the installer writes it into each assistant's global config file: `~/.claude/CLAUDE.md` for Claude Code, and `~/.config/opencode/AGENTS.md` for OpenCode (`$XDG_CONFIG_HOME/opencode/AGENTS.md` when that variable is set). Both get the same block, between `<!-- asdt:agent-config -->` and `<!-- /asdt:agent-config -->`.

ASDT owns only the text between those markers:

- **No file yet**: the installer creates it with just the block.
- **Your own content, no block**: the block goes at the end, after a blank line. Your text stays byte for byte as it was.
- **A block already there**: it is replaced in place, and nothing outside it changes. Re-running with the same choices writes the same bytes.
- **Damaged markers** (one marker without the other, a marker twice, or the end before the start): the installer writes nothing and reports the error, so you can fix the markers by hand. It never adds a second block.

A marker counts only when it sits alone on its own line, so mentioning one inside a sentence of your own text is harmless. Writes are atomic (temp file + fsync + rename), keep the file's mode, and follow a symlinked `CLAUDE.md` / `AGENTS.md`: the link stays and the file it points to is updated.

When the file already exists, the installer asks per assistant: **Update ASDT block** (the default) or **Skip**, which leaves the file untouched.

The block loads in every session, including projects that don't use ASDT, so it holds only user-level preferences: the persona's voice, your emoji and language choices, and a few rules that apply anywhere (short answers by default, confirm before irreversible actions, push back once and then defer to you, no `Co-Authored-By` lines). One line points to `/asdt` and its specialists for projects with an `.asdt/` directory. The specialists carry their own rules.

To take it out, open **Dashboard** from the main menu, where assistants with a block show an `agent config` badge, and press `r`, then `enter` to confirm. That removes the block and the blank line before it. The rest of the file is byte for byte what it was before the install, except that a missing final newline is added. The file itself stays, even if nothing is left in it.

### Executor agents on both

Both assistants receive the same two executor agent *types*, rendered into each tool's format:

- **`asdt-analyst`** — read-only. It inspects the repo and returns one summary to the orchestrator, never writing a file. In Claude Code its `tools:` line is an explicit allowlist; in OpenCode it's `edit: deny`, `task: deny`, and a Bash allowlist (`git log`, `git diff`, `ls`, `grep`, ...) with a catch-all `deny`.
- **`asdt-builder`** — write-capable. It creates and edits files within its declared targets, then returns one summary. Its Bash is for inspection only — it never runs build, lint, test, install, or codegen; checks run at the Developer's verify gate. In OpenCode that's `edit: allow` with a `deny` for the scratchpad (below), `task: deny`, `bash: allow`.

**The scratchpad on OpenCode.** OpenCode has no session scratchpad of its own, so working summaries live in the temp fallback, `/tmp/asdt-{project}/{session}`, outside your worktree (see [Scratchpad & Memory](/asdt/docs/memory-and-engram#the-scratchpad-working-summaries)). Both agents get `external_directory` read access to exactly `/tmp/asdt-*/**` and `/private/tmp/asdt-*/**` (on macOS `/tmp` resolves to `/private/tmp`). The fallback is always under `/tmp`, never `$TMPDIR`, so the grant written at install time matches the path a run resolves later, and the agents can read the inputs they are handed. The builder's edit rule denies those same paths: only the orchestrator writes the scratchpad.

**No memory.** Neither agent gets memory tools: only the orchestrator (your main assistant) remembers and recalls (see below). In Claude Code the tool allowlist grants none. OpenCode hands MCP tools to sub-agents by default, so each agent's permission block denies every known provider's memory tools (for Engram, `*_mem_save`, `*_mem_search`, `*_mem_get_observation`, whatever the MCP server is named).

## How memory (Engram) is wired

ASDT uses a **memory provider** to carry the project's key knowledge (non-obvious decisions, debate conclusions, conventions, lessons, audit findings) from one session to the next. Today that provider is **Engram**, an MCP (Model Context Protocol) server. Within a session, specialists hand work to each other through the session scratchpad, not memory. See [Scratchpad & Memory](/asdt/docs/memory-and-engram) for the full model.

Memory is wired per assistant through **MCP configuration** — you add the Engram MCP server to whichever assistant you're using, following Engram's own setup guide. Only the orchestrator, your main assistant, uses it, so the Engram tools only need to be on its tool list. The installer writes the binding (for Engram, `mem_save` behind **remember**, `mem_search` then `mem_get_observation` behind **recall**) into the orchestrator-facing skill files, noting the plugin-scoped and bare MCP names Claude Code may expose them under. The tool names never reach a sub-agent: the orchestrator strips the binding out of any shared file it places in a sub-agent's prompt (see [Memory providers](/asdt/docs/memory-and-engram#memory-providers)).

ASDT does not hard-code an MCP config path for you: the exact file where MCP servers are declared is the assistant's concern, so follow your assistant's MCP setup docs. If Engram isn't reachable in a session, or you installed with **No memory**, specialists say so in one line and keep working from the scratchpad; nothing is recalled or remembered.

## After installing: reload your assistant

Newly installed skills, agents, and config are picked up when the assistant loads them. If you install (or re-install) while your assistant is already running, restart or reload it so it re-reads its skills and agents directories.

## How a new assistant is added (adapters)

Support for each assistant is expressed as a set of small **adapters** — that's the layer that lets ASDT speak each tool's native dialect. Adding a new assistant means adding an entry to each of these lists (all in `internal/installer/`):

- **`Descriptors`** — the assistant's identity and its skills root directory.
- **`AgentAdapters`** — how to render the executor agents into the assistant's native agent format.
- **`AgentConfigAdapters`** — the path of the assistant's global config file. The shared marker-block logic writes and removes the agent config there.
- **`CommandAdapters`** — optional; only assistants that need generated command wrappers carry an entry (Claude Code carries none).

Anything assistant-specific lives in that assistant's adapters. Because each concern is a separate adapter list, a new assistant is additive: you implement its rendering and paths, register it, and the shared skill-copy, manifest, and prune logic apply to it unchanged.
