# Agent portability

ASDT installs one specialist skill tree into two different hosts — Claude Code and
OpenCode — without forking content per host. This document explains the seam that
makes that possible: a single embedded source of truth, and a set of thin adapters
that translate it into each host's native artifacts.

## Thesis — one embedded source of truth

The skill tree is embedded into the binary by `skill/embedded.go`:

```go
//go:embed SKILL.md asdt-*
var skillFS embed.FS
```

That directive bakes the root `SKILL.md` plus every `asdt-*` directory (specialists,
their scoped skills, and `asdt-shared`) into `skillFS`, exposed through `skill.FS()`.
This embedded FS is the single source of truth for specialist content. Adapters only
ever **read** from it and **write** host-native artifacts; they never own or mutate
the specialist content itself. Add a directory matching `asdt-*` and it ships on the
next build — no adapter edit required.

## Host registry

Known hosts live in one place: `Descriptors []AssistantDescriptor` in
`internal/installer/assistants.go`. Today that is exactly two entries —
`claude-code` (`AssistantClaudeCode`) and `opencode` (`AssistantOpenCode`). Each
descriptor carries the host's `ID`, display `Name`, `BinaryName`, and its skills
ROOT directory. Those roots are resolved **at runtime** from `$HOME` /
`$XDG_CONFIG_HOME` (`claudeSkillsDir()` / `openCodeSkillsDir()`), never hard-coded —
which is what lets the sandbox flow in [development.md](./development.md) redirect an
entire install by overriding `$HOME`.

## Adapter axes

Beyond the host registry, the host-specific behaviour is split across five
independent axes. Each axis is a small table or render function; a host opts in by
carrying an entry and opts out by simply not appearing.

**(a) Skill-tree copy — host-agnostic.** The core install copies each top-level entry
of the embedded skill tree to its own sibling directory under the host's
`SkillsDir`. This step is identical for every host; there is no per-host branching
in the copy itself.

**(b) Command wrappers — `CommandAdapters` (`adapters.go`).** OpenCode needs extra
discoverability artifacts: a `commands/` wrapper per specialist, generated by
`generateOpenCodeCommands` from each `SKILL.md`'s frontmatter
(`parseSpecialistFrontmatter` → `renderOpenCodeWrapper`). Claude Code needs none, so
it carries **no entry** in `CommandAdapters` — absence is the no-op idiom. The table
is the registry; you read intent by what is and isn't present.

**(c) Executor agents — `agent_adapters.go`.** Both hosts get executor agent
definitions (`asdt-analyst`, `asdt-builder`), but in different native formats.
`renderClaudeAgent` emits Claude Code's `tools:` allowlist frontmatter;
`renderOpenCodeAgent` emits OpenCode's `permission:` block. Both delegate to the
shared `writeAgentBody`, which bakes the same executor header and constraint prose
into every body — so the agent's *behaviour contract* is shared while only its
*serialization* differs per host.

**(d) Global agent config — `agent_config_adapters.go`.** Claude Code's global config
is injected as a marked block (`<!-- asdt:agent-config -->` … `<!-- /asdt:agent-config -->`)
into `~/.claude/CLAUDE.md` via `writeClaudeAgentConfig`, so the host's native config
file is updated idempotently and can be cleanly removed. OpenCode instead reads a
dedicated `AGENTS.md`, written by `writeOpenCodeAgentConfig`. Same intent, two native
homes.

**(e) Model-ID translation — `ai_providers.go`.** A selected model is one
`AIModel{ID, ClaudeCodeEnum, OpenCodeID}`. The `ID` is what gets written into a
workflow step's `model:` field; `OpenCodeID` is the `provider/model` string OpenCode
consumes directly, while `ClaudeCodeEnum` (`haiku`/`sonnet`/`opus`) is what Claude
Code maps to at invocation time. One catalog entry, both host dialects.

## What "thin" means

Each per-host entry carries **only** what is native to that host on that axis — a
serialization format, a config-file location, a model dialect. No business logic, no
specialist content. The shared parts (the skill copy, the executor body, the model
catalog) stay shared. And on any axis where a host needs nothing, **absence is the
no-op**: there is no empty stub, no `if host == X { return }` scattered through the
core — the host simply doesn't appear in that axis's table.

## Adding a host

To support a third host, you add only native glue — never specialist content:

1. One `AssistantDescriptor` in `assistants.go` (ID, name, binary, skills root) plus
   its runtime root resolver.
2. A per-axis entry wherever the new host needs that axis: a `CommandAdapters` entry
   if it needs command wrappers, an `AgentAdapters` entry plus a `render…Agent`
   function and an `agentRootFor` case for executor agents, an `AgentConfigAdapters`
   entry for global config, and an `OpenCodeID`-equivalent field path for model
   translation.
3. Nothing under `skill/` changes. The embedded specialist content is untouched —
   you are only teaching the installer how to serialize the existing source of truth
   into one more native shape.
