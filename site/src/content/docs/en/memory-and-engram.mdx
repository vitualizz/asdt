# Knowledge Base & Memory

## Why memory matters

Without persistent memory, every specialist starts from scratch. The Developer can't read the Architect's decision record. The QA specialist doesn't know what the Developer built. You'd have to manually copy context between every step — which defeats the purpose of a team.

ASDT solves this with a knowledge base. Every artifact a specialist produces is saved with a stable key. The next specialist retrieves it automatically by key. Context flows forward without manual intervention, even across sessions separated by days.

## How knowledge flows

Every specialist run saves one hand-off. It is stored in the knowledge base with two identifiers:

- A **human-readable title** — e.g. `"add-auth/developer/handoff"`
- A **stable key** for machine retrieval — `{project}/{change}/{role}/handoff`, used by subsequent specialists to fetch exactly the hand-off they need

When the next specialist runs, it queries the knowledge base by key. If the artifact exists, it proceeds normally. If it's missing, it notes the gap in `open_items` and continues with available context — no hard failures, no blocked pipelines.

This means run order is flexible. You can start with any specialist. You can pause between steps — even switch assistants — and the knowledge base holds the state. An artifact saved from Claude Code is readable by a later step run in OpenCode, and vice versa, because both read and write the same memory provider's store (Engram, today).

## Memory providers

ASDT requires a **memory provider** — a persistent store that survives session boundaries and makes artifacts available across different specialist invocations.

A memory provider gives ASDT:
- **Cross-session persistence** — Monday's Architect output is available to Thursday's Developer
- **Project scoping** — artifacts from different projects don't mix
- **Key-based retrieval** — a specialist picks a record by its exact key, never by how closely it matches

Today, **Engram** is the supported memory provider. More providers are planned.

### How ASDT talks to memory

No specialist prompt names a provider. The prompts speak a small **memory interface** of three verbs, defined once in the shared protocol:

- **save** — store a record under its stable key. Saving to a key that already holds a record replaces it (an upsert).
- **search** — find records by key prefix (`{project}/{change}`) or by free text. Each match carries its key, so a specialist picks the one it needs by exact key.
- **get** — read one full record by the id a search returned.

When you install, the installer **binds** that interface to the provider you selected: it writes the provider's name, its `memory.provider` value, and the exact tool behind each verb into the installed protocol (and so into every specialist), the executor-agent definitions, `/asdt-init`, and the `/asdt` router — and grants those same tools to the `asdt-analyst` and `asdt-builder` agents. A specialist never guesses a tool name: the binding in front of it says which one to call. Supporting another provider is a change to the installer alone — see [Development](/asdt/docs/development#adding-a-memory-provider).

### Engram — current implementation

[Engram](https://github.com/Gentleman-Programming/engram) is an MCP (Model Context Protocol) server that provides persistent, project-scoped memory for AI assistants.

Engram must be running before you invoke any specialist (or whichever memory provider you have configured). Artifacts saved to Engram survive the end of an assistant session — that is the property ASDT depends on for cross-session pipeline continuity, whether you run Claude Code or OpenCode.

#### Installation

Follow the [Engram setup guide](https://github.com/Gentleman-Programming/engram) to install and start the MCP server. Then wire it into your assistant's MCP configuration — Claude Code and OpenCode each expose their own MCP setup, so follow the one for the assistant you use. Both connect to the same Engram server; only the wiring location differs.

#### Verifying it's running

```
/asdt-init
```

The init specialist checks that the session holds the memory provider's tools before anything else; if they are missing, it explains how to connect the provider and stops without writing config.

When a specialist needs a prior artifact, it runs a memory **search** for the artifact's key (the exact label used to save and re-find it) — with Engram, `mem_search`, where the key travels as `query` (it was saved as `topic_key`). Search can return near misses, so the specialist keeps the match whose key is exact — Engram shows it as the match's `title`, the key without its leading `{project}/` — then runs a memory **get** with that match's id to pull the full content (`mem_get_observation` with Engram). The exact key decides, never the ranking, and nothing beyond the declared records is scanned.

## Cross-session continuity

Picking up a pipeline after a session ends is the same as continuing it mid-session:

```
/asdt-developer Implement based on the Architect's ADR
```

The Developer searches the knowledge base for the Architect's hand-off by key. If found, it proceeds normally. If not found, it notes the missing input and proceeds with available context.

The same holds for the Developer's own plan. A plan is saved under the Developer's key before anything is written, so a later session can pick it up where it stopped:

```
/asdt-developer "implement the plan we approved"
```

It finds the saved spec and goes straight to the approval gate — or, when the plan was already built but never checked, straight to verification. Once built, the same key holds what was written and how verification went.

Session boundaries don't matter. Monday's Architect output is as readable to Thursday's Developer as if they'd run back to back.

## Project scoping

Every key a specialist saves under — through the memory **save** verb, `mem_save` with Engram — starts with the project name (`{project}/…`). ASDT derives the project name from `.asdt/config.yaml` or the directory name. Artifacts are searchable within a project scope — running ASDT on two different projects doesn't mix their memory.

## What Engram is not

Engram is not a file system. Artifacts are documents, not code files. When the Developer writes code, it writes real files to your repository — only the ones you approved — and its hand-off records which files changed and why. When it has no files to write (a plan with no declared targets), the code comes back as snippets inside the Engram document — specifications for what to write, not files on disk.

This separation is intentional. Code files have git history. Artifacts have the knowledge base. Both live where they belong.
